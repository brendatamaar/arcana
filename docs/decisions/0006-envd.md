# 0006: `envd`, the in-sandbox gRPC daemon

Status: accepted. Date: 2026-11-15. Tasks: T4.1. The gRPC, protobuf and proto-compiler
dependencies and raw `AF_VSOCK` syscalls were approved by the owner on 2026-11-15.

The Firecracker driver (T4.2) has no Docker exec to borrow: the host needs a way to run
commands, move files, stream output and signal process trees inside a microVM. `envd`
is that agent. It grows out of [`sbx-exec`](0002-exec-helper.md) rather than replacing it.

## Shape

- **One binary, shared code.** The controller and file utilities moved from
  `cmd/sbx-exec` to `internal/sbxexec` (stdlib only). `sbx-exec` is now a thin `main`
  over it, so the Docker path keeps its proven behaviour and its checksum-verified
  embedded binaries. `cmd/envd` contains the same subcommands plus `envd serve`.
- **The daemon spawns itself.** For every exec it launches `envd run …` as a child
  controller, which is the unchanged `sbx-exec run`: a child subreaper that adopts
  detached descendants, signals pidfd-verified identities and writes the status only
  after the kernel proves the tree is empty. A daemon that was itself the subreaper
  could not attribute descendants to one of several concurrent execs. Cancellation is
  the same controller-identity request as before, and the daemon applies the host
  acceptance rule of PRD §9.4 before reporting an exit: matching ID, cleanup marker and
  agreeing transport exit, otherwise `DATA_LOSS` so the host destroys the sandbox.
- **Files run in child processes too** (`envd write|read|ls|remove|mkdir`), after the
  same lexical validation against allowed roots. A daemon running as root therefore never
  opens a sandbox path itself, and symlinks resolve only in the sandbox's own namespace.
  The write utility removes its temporary file on SIGTERM so an abandoned upload commits
  nothing.
- **Privileges.** `--user uid:gid` makes every child run as that identity (the daemon
  must be root or already that user; root commands are refused). Children are
  non-dumpable subreapers like today. Anything in the guest that can reach the daemon can
  already run commands as the sandbox user, so the daemon adds no authority.

## API

`internal/envd/envdpb/envd.proto` (package `arcana.envd.v1`): `Info`; a bidirectional
`Exec` stream (start, stdin, stdin_close, resize, cancel in; started, output, exit out);
`Signal` (TERM with a bounded grace, or KILL, for control that does not queue behind
stdin back-pressure); `WriteFile`, `ReadFile`, `ListFiles`, `RemoveFile`,
`MakeDirectory`. A client that disconnects without an exit cancels the command and its
whole tree, as with the WebSocket protocol. TTY mode allocates a pty and runs the
controller with it as its controlling terminal, so job control is the one ADR 0002
verified.

Everything is bounded (AGENTS rule 8): 64 KiB chunks, 128 KiB receive messages, at most
64 concurrent execs and 16 file operations by default, the same argv/env/cwd/timeout
limits as the host orchestrator, the helper's file size, listing and metadata caps, and
a per-operation file timeout. Output is never retained; gRPC flow control backs a slow
reader up to the command's pipe.

## Transports

`unix:<path>` creates a socket with mode 0600 (via umask, with no window) and replaces
only a stale socket. `vsock:<port>` uses raw `AF_VSOCK` through `golang.org/x/sys/unix`
and accepts only CID 2 (the host): connections from the guest itself or another VM are
closed unanswered. There is no TLS because the transport is the trust boundary. Firecracker
exposes guest vsock to the host as a Unix socket with a `CONNECT <port>` handshake; that
dialer belongs to the driver (T4.2).

## Toolchain

Generated code is committed and checked by `make verify-generated`. `scripts/genproto`
compiles the `.proto` with `github.com/bufbuild/protocompile` (Apache-2.0, pure Go) and
runs the pinned `protoc-gen-go` and `protoc-gen-go-grpc` (`go tool`), so no `protoc`
install is needed and generated headers do not depend on a local compiler version.
gRPC and protobuf (Apache-2.0, BSD-3) are linked by `cmd/envd` and its tests; `sbx-exec`
stays stdlib-only, so the embedded helpers keep their size and reproducibility.

## Verified

Unit tests drive a real daemon over a Unix socket: streams, exit codes, binary output,
timeouts and cancel killing `setsid` descendants, disconnect cleanup and slot release,
`Signal`, TTY size and resize, limits and rejection paths, file round trips, path and
size limits, abandoned and oversized uploads. A test-only probe running inside hardened
containers (`make test-integration`) repeats the key checks under **runsc and runc**,
including the TTY and detached-descendant cases. Not verified: a real microVM, vsock
traffic from a host (no `/dev/kvm` here; the vsock listener has only a peer-policy unit
test and a loopback skip-test), and running the daemon as root with `--user`.
